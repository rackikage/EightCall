# Structured Command Schema and Enforcement Order

The command layer is where authorization is easiest to get wrong. The rule: **accept typed requests, never raw shell strings.** A gateway that takes a command string cannot reliably authorize it, because the same string can mean different things after shell expansion, quoting, globbing, or chaining (`;`, `|`, `&&`, subshells).

## Why not raw shell

```text
run("some command from a user")     # unacceptable: unvalidatable, injectable
```

Problems: arbitrary command execution, no parameter schema, no resource binding, no way to scope by environment, and audit records that capture an opaque string rather than an intent.

## Request schema

```json
{
  "request_id": "req_01",
  "actor": {
    "id": "user_123",
    "roles": ["operator"]
  },
  "action": "service.restart",
  "resource": {
    "type": "service",
    "id": "api-worker"
  },
  "environment": "staging",
  "parameters": {
    "graceful": true
  },
  "reason": "Deploy completed; restart is required to load the new release."
}
```

Field notes:

- `request_id` — unique, opaque, generated by the gateway (not the caller) and echoed into every audit record so a request can be traced end to end.
- `actor` — authenticated identity plus the roles resolved *at decision time* (never trusted from the request body).
- `action` — a member of the allowlisted command catalog, using a namespaced verb (`service.restart`, `secret.read`, `data.export`).
- `resource` — typed (`service`, `host`, `bucket`, `secret`) and bound to a concrete id, so scope checks have something real to evaluate.
- `environment` — `development` / `staging` / `production`; drives both role scope and approval requirements.
- `parameters` — validated against the action's strict schema; unknown keys are rejected, not ignored.
- `reason` — human justification, mandatory for sensitive actions, stored in the audit record.

## Enforcement order

```text
1. Verify identity and session validity.
2. Verify action is in the command allowlist.
3. Verify the actor's role permits that action on that resource.
4. Verify the environment and change window are permitted.
5. Validate parameters against a strict schema.
6. Decide whether human approval is required.
7. Execute through a fixed handler, never via arbitrary shell input.
8. Store a complete audit record.
```

Design notes:

- **Fail closed at every step.** A timeout on the approval service, an unparseable policy, or an ambiguous resource is a `DENY`, not a retry-until-permitted.
- **The gateway is not the executor.** Step 7 hands a *validated, structured* intent to a low-privilege worker that maps the action to a fixed handler. The worker cannot be talked into a different action.
- **No shell interpolation anywhere in the path.** Handlers receive typed arguments; if a value reaches a shell, it does so as a separately-quoted argument and only when the action's `shell_access` is explicitly `true`.
- **Deny with a reason.** Every denial returns a stable machine-readable reason (see `policy-schema.md`) and is logged at the same fidelity as a permit.
- **Step 8 runs on both paths.** A denied request is at least as interesting as an allowed one for detection.

## Handler contract

Each action maps to exactly one handler with declared properties:

```yaml
execution:
  handler: restart_service          # a named, code-reviewed function
  shell_access: false               # no shell unless explicitly justified
  timeout_seconds: 60
  network_egress: deny              # default no egress
  filesystem: read-only             # least privilege
  runs_as: svc_restart_worker       # dedicated, low-privilege identity
```

The handler's declared capabilities are the *ceiling* for that action. Anything the handler needs beyond them is a design change that goes through review, not a runtime decision.
